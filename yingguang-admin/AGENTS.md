# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

`prototype.html` is a separate `file://` deliverable. After every source change, run `npm run build:standalone`; its IIFE build must replace `process.env.NODE_ENV` for the browser. Do not treat a successful bundle as sufficient verification: load `prototype.html` in a real browser and confirm `#root .app-shell` is rendered, because unresolved Node globals produce a blank page under `file://`.

The canonical business behavior for this prototype is:

- Do not add a separate `是否可领` field. Creator-facing availability is derived from task status: only `进行中` tasks are shown in the task square and accept new favorites or mounts.
- Task statuses are `待启动 / 进行中 / 已暂停 / 已关闭`. Plan statuses are `创建中 / 创建失败 / 待启动 / 进行中 / 已暂停 / 已关闭`.
- On first activation, a task moves from `待启动` to `进行中` automatically once the plan/time/series/asset conditions are met. If a task was paused because its asset became invalid, the same asset becoming effective again auto-restarts the task (series listed, plan/time still met, not operator-paused, not PA-locked). A series going back online after delisting does not auto-restart. An operator pause is never overwritten by an upstream recover. PA conversion creates a locked pause that no operator or plan-level action can restart.
- A PA reservation does not pre-create the target asset or target task. Before the switch, only the existing asset A1 is selectable and only T1 exists. At the switch, the operator platform invalidates A1, creates A2 and makes A2 effective immediately; Yingguang then creates T2. T1 becomes `已暂停` with `pauseReason=PA转换` and `canRestart=false`, while T2 inherits the confirmed plan configuration and relationships. Do not represent T1 as `已关闭`; that status is reserved for a true terminal end. This is a frozen decision (2026-08-14), not an open question. When `canRestart=false`, the 开启 button stays greyed out and carries a hover reason: `旧版本已完成转换，任务不可重启` for a PA lock, `当前任务不可开启` otherwise.
- Keep pause reason, blocking conditions, and `canRestart` as internal task-control data; do not add a fixed “状态说明” field to the task list.
- Match the current online interaction containers: plan detail opens in a right drawer, task detail opens as a full page, create/edit uses a full-page form, rule preview uses a modal, and row operations are `查看 / 暂停或开启 / …（编辑、结束）`.
- Product wording “distribution version” maps directly to the operator-platform technical object `asset`, whose unique identity is `asset_id`. In JavaScript state use `assetId` / `assetIds`; never introduce `versionId`, `versionIds`, or a second fake version identity.
- A plan is created by selecting one or more short dramas that currently have an **effective revenue-sharing** (`分账`) asset. Traffic-only and publish-only assets, and pending/invalid 分账 assets, are not selectable and do not create tasks. After selection the page auto-resolves exactly one current effective 分账 `assetId` per `seriesId` (1:1). Do not show “切换展示版本”, recommendation tags, or an operations column on the selected-series table. The plan list “短剧（部）” and “分账版本（个）” counts must stay equal. The plan-detail drawer merges 分销版本 and 网盘链接 into a single table.
- Submitting a manual plan automatically creates one task per selected short drama using its resolved effective 分账 `assetId`. At creation, every generated task name inherits the plan name; tasks under the same plan may therefore have the same name and are distinguished by task ID and short drama. After creation, keep the plan name, drama range, and current asset bindings locked; a PA event is the system-only exception that replaces A1 with A2 in the plan's current asset binding and creates T2. Material links and participation rules remain editable.
- A task split from a manually submitted plan still uses the source label `手动创建`, with `sourceId` equal to the originating plan ID. Do not relabel it as `计划创建`. `自动创建` is reserved for tasks emitted directly by an automatic rule; those tasks have no plan relationship and must not expose a fake `planId=0`.
- Second-creation material links remain short-drama-level data. PA replacement reuses the existing short-drama material row; the create selector, plan list and plan detail must never show A1 and A2 as simultaneous current versions. Historical A1/T1 may remain internally queryable, and T1/T2 may coexist as historical task records after conversion.
- This is a Yingguang-side operations redesign, not a copy of the operator-platform asset-management UI. The task list may expose the business-facing “版本名称” dimension and filter by it; it must not expose the technical `assetId`, asset status, or sales-method fields. Task detail remains focused on task/short-drama information and does not透传 those asset-management fields.
- Do not add “状态说明” or “履约概况” columns to the task list, and do not add a fulfillment overview section to task detail.
- **Multiple-drama** create uses Excel bulk upload (columns: 短剧 ID + 网盘链接); imported links are read-only in the selected-series table — do not show a separate per-drama 网盘 input block. **Single-drama** create still uses one manual 网盘 field. **Edit plan**: show 网盘 in the selected-series table with an inline edit icon per row (view link + pencil → bordered input on click); every selected drama must already have a 网盘 link (no empty/— state).
- The task list also places “版本名称” and “短剧名称” next to each other, and its filters expose both dimensions. Historical PA tasks may therefore show the old business version name in the task list even though the create selector only offers the currently effective asset.
- The task list exposes PA relationships via “关联任务”: when a related task exists, show `转换自 / 转换为 + 任务名称与ID`; the task name opens its detail. No separate “是否转换售卖方式” column.
- On the create-plan page, do not show implementation-facing explanations such as “版本技术对象为 asset” or the redundant short-drama material-deduplication tip. Keep the unselected material area as a neutral empty state.
- The verified online task flow is `… / 编辑` → full-page task detail edit state → pencil beside the web-drive link → “修改网盘链接” modal; no other editable field was visible. For this refactored Demo, intentionally streamline that flow per product-owner feedback: row `… / 编辑` opens the short-drama-level link modal directly from the task list. This is a deliberate redesign, not a claim about current online behavior.
- The task-detail page in this Demo shows the web-drive material link as read-only and must not include a pencil/edit entry. The list edit modal includes a checked-by-default option “同步更新其他计划中该短剧的素材链接”. When checked, save updates every plan containing the same `seriesId`; when unchecked, only the current plan is updated. A historical PRD once described task end time as editable, but that control is absent from the currently verified online UI; keep it read-only unless the product owner reconfirms otherwise.

- 创建计划页不展示「已选短剧及生效版本」模块。单选保留短剧下拉和素材链接输入；多选上传区域内仅展示导入短剧及素材链接，支持清空、重新上传，切换到多选时清空单选结果。编辑计划的版本及素材维护保持原有行为。
